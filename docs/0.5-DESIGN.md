# 0.5.0 Linux privacy and delivery design

Implemented in the 0.5.0 Linux source and packages. This document records the privacy boundaries, not an independent security audit. See [validation results](0.5-VERIFICATION.md).

## Defaults

Ephemeral, independent identities per lobby; RAM-only chat/trust; no mailboxes; no organization issuer. Direct exposes IP addresses. Tor never invokes a Direct, DHT, DNS or clearnet-issuer fallback. Persistent settings remain separate from secret storage. No Windows/macOS client in this milestone.

## Storage

Persistence requires an explicitly opened encrypted vault and an explicit per-lobby identity opt-in. A random vault encryption key is held by the Linux Secret Service through libsecret's `secret-tool`; absence/lock/error fails closed. A bounded versioned file holds independently generated lobby signing seeds, saved invitation capabilities, sender sequence reservations, optional outbox/mailbox records and durable-message deduplication. All are encrypted with RustCrypto XChaCha20-Poly1305 using fresh OS-random 192-bit nonces and authenticated headers. No plaintext spill file, automatic persistence or chat log. Noise static keys and onion services remain fresh each process/lobby join. Trust stays in RAM.

Private directories/files, exclusive process locking, bounded decoders, atomic replacement and file/directory synchronization prevent ordinary concurrent writers and partial commits. Monotonic signing sequence ranges are durably reserved before use. Restoring an old backup is not protected by a hardware rollback counter: rotate that lobby identity after restoring old state. Same-account processes, an unlocked/misconfigured Secret Service and a compromised OS remain in the trust boundary. Deleting records is not a guarantee against SSD snapshots or backups.

Encryption does not conceal vault existence, file length, write timing or the application's keyring label. The provider may copy key material internally; the vault key's reported memory-lock status does not cover every temporary buffer. A nondecreasing persisted clock floor prevents ordinary backward-clock changes from reviving expired records, but a restored old snapshot can roll that floor back too.

## Delivery and peer mailboxes

Live messages get bounded retry and signed receipt status. A receipt means a peer accepted the signed message, not that a human read it or that every participant received it.

Durable delivery is opt-in and requires a persistent lobby identity. Each durable signed message authorizes retention for at most 24 hours. A bounded encrypted sender outbox survives restart. Separately opted-in peer mailboxes may retain those messages and replay them over authenticated Noise lobby sessions. Mailbox storage acknowledgements are distinct from recipient receipts. Live-only messages are never intentionally written by this feature. Full queues reject new durable work; errors do not downgrade to plaintext storage.

A mailbox is an authorized lobby participant and can read lobby plaintext. It is not a central server and makes no availability promise. Offline delivery requires a reachable participant holding the message and a reachable seed; no delivery is possible when every relevant peer is offline. Durable lobby messages can reach participants authorized to join that same lobby before expiry. There is no permanent history synchronization. Expiry depends on the wall clock; signatures, IDs and sequence checks provide separate authenticity/replay controls. Durable duplicate state is bounded and persisted before acknowledgement/display when persistence is enabled.

## Private lobby rotation and revocation

Managed private cards pin the creator's lobby-scoped administrator public key. Only that key can authorize a replacement capability. Rotation requires every retained direct neighbor's fingerprint to be explicitly verified; an old capability holder can create unverified aliases, so shared-capability possession alone cannot qualify a replacement recipient. Rotation creates a fresh capability, rendezvous ID, lobby identity and endpoint. The replacement invite is individually encrypted to retained verified, currently authenticated direct neighbors; never gossip a replacement secret to the old lobby. Excluding a fingerprint withholds the new invite from that identity. Old streams/endpoints are closed, and the local old capability/outbox/mailbox are retired. Trust and organization attestations do not transfer automatically.

Offline or indirectly connected retained users need a fresh invite through an appropriate channel. Revocation protects the replacement lobby, cannot erase old plaintext, cannot stop former members running a fork of the old lobby and cannot stop a retained member deliberately leaking the new capability. A disconnected former identity can rejoin only if someone gives it the new capability; nicknames are not revocation identifiers. Failure during transition is visible and never causes automatic reuse of the old capability or a transport change.

## Optional organization membership

Use a dedicated offline organization issuer, independent from release-signing keys. A bounded COSE_Sign1 Ed25519 credential binds an explicitly trusted issuer, lobby ID, lobby public key, enrollment challenge, coarse organization/role, random serial and a short lifetime. Enrollment requests prove possession of the lobby signing key. No global personal identifier or email is required or transmitted. An issuer can correlate its enrollments; group membership itself is metadata.

The client imports credentials locally and exchanges them only inside authenticated Noise. Verification is scoped to a manually selected issuer for the current lobby and remains separate from human fingerprint verification and private capability admission. No synchronous CA call, global trust installation or automatic issuer lookup occurs. Default operation does not require an organization or CA. XXC's existing generic certificate/release APIs are not assumed to implement this dedicated membership policy; the initial issuer is separate Rust offline tooling. Any future live XXC enrollment needs its own reviewed policy and Tor-only access design.

## Compatibility and validation

New mandatory protocol/card versions fail cleanly with unsupported peers. No plaintext or weaker-cipher fallback. Acceptance tests cover tampered/cross-lobby membership credentials, unauthorized rotations, excluded peers, restarted identity/sequence state, encrypted storage/tampering/permissions/locking, mailbox consent/expiry/quotas, duplicate receipts, recovery after reconnect and Tor policy instrumentation. Longer fuzz/load campaigns use synthetic data only. Existing independent-audit limitations still apply.
